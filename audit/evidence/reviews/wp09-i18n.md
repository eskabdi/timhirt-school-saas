## FINDINGS

**I18N9-1 (Medium): keyboard focus drops to the top of the page at every step of the approval inbox**
- **Where:** /home/user/rv-wp09/src/features/approvals/ApprovalsPage.tsx:178-203
- **Scenario:** A checker using the keyboard focuses "Reject" and presses Enter. The ternary swaps the `<Button>` for a `<>…</>` fragment, so React unmounts the focused button. Focus goes to `<body>`. The new reason textarea gets no focus and nothing is announced. The same thing happens on "Cancel" and on "Approve" (the `canDecide && !result` block unmounts).
- **Evidence:** I ran a scratch happy-dom test (/tmp/rv5-wp09-i18n/t/focus.test.tsx) that rendered ApprovalsPage with a pending request. It printed `after reject click, rej connected: false active: BODY`, then `after cancel click, active: BODY`, then `after approve, active: BODY`. This breaks WCAG 2.4.3 (Focus Order). After each step the user has to tab back through the whole sidebar.
- **Fix:** When Reject opens, move focus to the textarea (a ref and an effect, or `autoFocus`). On Cancel, send focus back to Reject. After a decision, focus the `role="status"` outcome (`tabIndex={-1}`) or the card heading. Keep the button elements stable rather than swapping in a fragment.

**I18N9-2 (minor): payment errors can show English or misleading text**
- **Where:** /home/user/rv-wp09/src/features/fees/InvoiceDetailPage.tsx:193-198 and :195
- **Scenario A:** WP-09 added a 2-decimal limit and a 10,000,000 cap to `record-fee-payment` (index.ts:43). The client does not check either. If someone types `100.555`, the client checks pass and the server returns `errors.badRequest()`, which is `{error:"Invalid request"}`. The page shows that English text verbatim in the am and om UI. FS-3 described this raw fallback in general; this is a new input that reaches it.
- **Scenario B:** `amount_exceeds_balance` maps to `fees.errors.overpayment` ("Amount exceeds the outstanding balance"). Take a 1,000 invoice with 600 waiting for approval: the payable amount is 400. Entering 500 gives that message, even though the balance on screen is still 1,000. A key that explains the case, `approvals.error.amount_exceeds_balance` ("…counting payments waiting for approval"), exists in all three locales but is never used.
- **Fix:** Check for 2 decimals and the cap on the client, using `fees.errors.invalidAmount`. Map `amount_exceeds_balance` (both the client check and the server code) to `approvals.error.amount_exceeds_balance`. Map any other code to a translated generic message, not the raw text.

**I18N9-3 (minor): Amharic plural uses a plural verb for one item**
- **Where:** /home/user/rv-wp09/src/locales/am/common.json, key `gradebook.correctionsFailed`
- **Evidence:** The string is `{count, plural, one {# ውጤት} other {# ውጤቶች}} አልተላኩም፦ {reason}`. For count=1 it renders "1 ውጤት አልተላኩም", a plural verb with a singular noun.
- **Fix:** Move the verb inside each branch: `one {# ውጤት አልተላከም} other {# ውጤቶች አልተላኩም}`.

**I18N9-4 (minor): the gradebook does not say which rows failed**
- **Where:** /home/user/rv-wp09/src/features/gradebook/GradebookPage.tsx:156-160
- **Scenario:** A teacher submits 3 corrections and 1 fails. The page shows only the count and the reason of the first failure (`failed[0].key`). It does not say which student failed and does not set `aria-invalid` on the row. The rows that went through fall back to the old score with no "pending" marker, so they look as if the edit was lost. If two rows fail for different reasons, the second reason is never shown.
- **Fix:** Mark each failed input with `aria-invalid` and a per-row message linked by `aria-describedby`. Show a "pending approval" note on rows that were submitted.

**I18N9-5 (minor): the transfer modal shows a stale success message**
- **Where:** /home/user/rv-wp09/src/features/students/TransferStudentModal.tsx:25,38,58, with StudentDetailPage.tsx:357
- **Scenario:** The modal stays mounted while closed, and `submitted` is never reset. After a successful request the only way out is a button still labelled "Cancel". Reopening the modal shows "Transfer request sent…" above an empty form.
- **Fix:** Reset `submitted` and `error` when `open` changes. Relabel the button "Close" after success, or close the modal and show the notice on the page.
